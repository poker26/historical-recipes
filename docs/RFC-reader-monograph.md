# RFC: «читательский монограф» — предрасчётная grounded-генерация вместо сырой агрегации

Статус: **Proposed** · Автор: «Что растёт» (клиентский агент) · Создан: 2026-06-10

> Развивает `RFC-field-view-data-noise.md` (QA, done) и `RFC-monograph-deepen-links.md`
> (Part A был отложен). Встраивается в `RFC-data-quality.md` («линтер гербария»,
> Фаза 0 в проде). **Эталон всего документа:** монограф читает обычный человек,
> которому должно понравиться приложение. Не агент, не админ — человек в лесу.

---

## 1. Проблема — `?view=field` для богатых растений читается как дамп

`GET /api/plants/{id}?view=field` сейчас — детерминированная агрегация: дедуп
точных строк + ранжирование. Для бедных растений это ок. Для богатых —
разваливается. Разбор живого ответа по **Хмелю обыкновенному**
(`fb743008-7884-4087-a35e-4dd7360e0c09`, 2026-06-10):

| Что | Сейчас | Норма для человека |
|---|---|---|
| Размер payload | **277 КБ** | единицы–десятки КБ |
| `uses[]` | **133** действия | ~8–12 *реально различных* |
| Морфо-дубли в действиях | «улучшает / улучшающее / улучшение пищеварения» — 3 записи одного; «успокаивающее»/«седативное», «болеутоляющее»/«обезболивающее», «бактерицидное»/«антибактериальное» — синонимы порознь | склеено в одно |
| `compound_groups[]` | **48** групп; шесть «горьких» («горечи / горькие вещества / горькое вещество / горькие / горькие кислоты / горечи, смолы»); «эфирное масло» + «эфирные масла»; группа с именем `None` (19 сирот) | ~15 настоящих групп |
| `parts_used` | 26 шт: «шишка/шишки/шишечки/соцветие/соплодие/соплодия/лупулин/люпулин/иллики/железки зрелых **нишек**» | ~5 (шишки, лупулин, листья, побеги, корень) |
| Вердикт | `🍽 съедобно` **и** `☠ ядовито` одновременно | одна честная фраза |
| `fun_fact` | `null` (а в цитатах лежит «хмель — северный виноград») | живой факт |
| OCR-шум | «нишек», «иллики», «лупулинъ», «рех-пятилопастные» протекают к юзеру | вычищено |
| Заглушки | «Описание появится позже» у веществ, `action_definition: null` | нет заглушек |

Что **уже хорошо** и трогать НЕ надо: ранжирование по числу источников (топ-5,
который видит человek, точен), цитаты с дозировками, чистка МКБ-кодов, фото,
структура `cautions`, рецепты-ссылки, кулинария.

Вывод: проблема не в данных (фактура богатая и обоснованная), а в том, что
**детерминированный дедуп слишком мелкий** (точные строки, не морфоварианты /
синонимы / OCR), **не ограничивает объём** и **не умеет писать человеческий
текст**. Нужен слой, который превращает обоснованную фактуру в приятный текст.

---

## 2. Решение

**Предрасчётная, grounded, review-gated генерация «читательского монографа»,
которая хранится в БД. `?view=field` отдаёт ХРАНИМЫЙ монограф, а текущая сырая
агрегация становится ВХОДОМ для генерации, а не выходом для пользователя.**

Решающий факт (явно подтверждён владельцем): **корпус БД в основном сформирован**
и меняется редко (единичные книги). Это делает предрасчёт строго лучше генерации
на лету.

### Почему пакет, а не «лениво по запросу + кэш»
- **Ревью до показа.** У проекта есть история галлюцинаций (фейковые рецепты в
  Анищенко-1980; класс «жидовская вишня»). При ленивой генерации первый
  пользователь каждого вида видит непроверенный LLM-вывод — галлюцинация доходит
  до людей. Пакет позволяет прогнать всё через publish-gate ДО показа.
- **Стабильный корпус → у лени нет выгоды.** Ленивость окупается при постоянно
  меняющемся/огромном-редком контенте. У нас фиксированный набор; один прогон
  амортизируется в ~ноль за просмотр.
- **Детерминизм для пользователя** (все видят один выверенный текст) и **нулевая
  латентность** (чтение из БД, без LLM в лесу).

Ленивый+кэш — только фолбэк, если пакет не запустить.

## 3. Пайплайн (4 шага)

```
[ source-grounded факты в БД ]
      │  (1) детерминированная дистилляция — то, что уже умеет _field_view
      ▼
[ компактный отранжированный набор фактов + цитаты + источники ]   ← вход LLM, НЕ 277 КБ
      │  (2) LLM-полировка (строго абстрактивная: склейка/чистка/проза)
      ▼
[ кандидат «читательского монографа» ]
      │  (3) grounding-guard + линтер (data_quality_findings) — P0 блокирует
      ▼
[ опубликованный монограф в БД ]  ──(4)──►  ?view=field отдаёт его
```

1. **Дистилляция (детерминированно).** Берём текущую агрегацию, но с двумя
   добавлениями: (а) точечный дедуп уже есть; (б) **жёсткий cap** — топ-N действий
   по числу источников (напр. N=12), топ-M групп состава, и т.п. На вход LLM идёт
   компактный, уже отранжированный набор фактов, каждый со своей цитатой и
   источником. Это держит токены низкими и LLM — на коротком поводке.
2. **LLM-полировка.** См. контракт в §5. Задача строго абстрактивная: склеить
   морфо/синоним-дубли, схлопнуть синонимы состава, починить OCR, нормализовать
   части, написать лид и «Интересное» из реальных цитат, разрешить противоречие
   вердикта. **Ничего не выдумывать.**
3. **Grounding-guard + линтер.** Прогон через `data_quality_findings`: каждый
   вынесенный факт должен прослеживаться во входе; P0 (ungrounded-claim,
   identity-конфликт) блокирует публикацию. Первый батч — выборочный ручной
   просмотр, далее доверяем guard.
4. **Хранение + отдача.** Монограф пишется в БД с хэшем входных фактов (§7).
   `?view=field` читает его напрямую.

## 4. Контракт хранимого «читательского монографа»

Заменяет сырую выдачу. Capped, человеко-ориентированный. Форма (эскиз, не код):

```jsonc
{
  "id": "...", "name": "...", "name_latin": "...", "family": "...",
  "photo_url": "...", "photo_attribution": "...",

  // НОВОЕ: одна честная фраза-вердикт вместо противоречивых бейджей.
  // Решает кейс «съедобно+ядовито» Хмеля.
  "verdict": "Молодые побеги съедобны (готовят как спаржу). Шишки —
              лекарственные, но в больших дозах действуют одурманивающе,
              поэтому есть ограничения.",
  "roles": ["edible","medicinal"],          // бейджи приводим в соответствие с verdict
  "is_toxic": false,                         // пересмотрен identity-чеком (см. §8)

  "description": "…почищенный текст, OCR исправлен…",

  "lead_fact": { "text": "Во Франции хмель зовут «северным виноградом».",
                 "source": "…" },            // = бывший fun_fact, теперь ВСЕГДА заполнен или отсутствует

  "uses": [                                  // ~8–12 РЕАЛЬНО различных, синонимы слиты
    { "action": "успокаивающее",            // канонизировано (седативное/успокаивающее → одно)
      "summary": "Снимает нервное возбуждение, помогает при бессоннице.",  // человеческая фраза
      "indications": ["бессонница","нервная возбудимость"],
      "quote": { "text": "…одна лучшая цитата с дозировкой…", "source": "…" },
      "source_count": 57 },
    …
  ],

  "compounds": [                             // ~15 настоящих групп, синонимы схлопнуты
    { "group": "горькие вещества",
      "note": "Лупулин и гумулон — дают горечь, отвечают за успокаивающее и
               противомикробное действие." },   // короткое человеческое «что это»
    …
  ],

  "cautions": { "text": "Не применять при беременности и кормлении; при
                         передозировке — тошнота, головная боль, разбитость.",
                "toxic_parts": ["шишки в больших дозах","лупулин"] },  // одна формулировка, не 22 обрывка

  "harvest": { … }, "culinary": [ … ],       // почищено и сжато
  "recipes": [ { "id":"…","label":"…" } ],   // детерминированные ссылки — НЕ трогаем
  "sources": ["Носаль 1960","Махлаюк 1992", … ],  // атрибуция для доверия

  "generated_from_hash": "sha256:…",         // хэш входных фактов (§7)
  "model": "…", "reviewed": true
}
```

Принципы формы: **cap на всё** (нет 133/48), проза вместо обрывков, один вердикт,
обязательная атрибуция источников (доверие).

## 5. Контракт для LLM (промпт-контракт)

- **ВХОД:** дистиллированный набор фактов из шага 1 — отранжированные действия с
  индикациями и **вербатим-цитатами + источником**, группы состава с примерами,
  части, описание, кулинария, cautions. Всё уже обоснованное.
- **ЗАДАЧА:** переписать это в `reader-monograph` (§4). Строго:
  - склеить морфологические и синонимичные дубли действий и групп состава
    (правило: если различие только в падеже/числе/очевидном синониме — одно);
  - починить очевидный OCR (нишек→шишек, лупулинъ→лупулин, «рех-»→«трёх-»);
  - нормализовать `parts_used` до коротких канонических форм;
  - написать `verdict`, `description`, `uses[].summary`, `compounds[].note`,
    `lead_fact`, `cautions.text` — **человеческим языком**;
  - выбрать по одной лучшей цитате на действие (с дозировкой/способом).
- **ЖЁСТКИЕ ОГРАНИЧЕНИЯ (anti-hallucination):**
  - **НЕ вводить ни одного факта, которого нет во входе.** Перефразирование и
    реорганизация — да; новые свойства/показания/вещества — нет.
  - Не давать медицинских инструкций/дозировок «от себя» — только то, что есть в
    цитатах источников.
  - `lead_fact` — только из реального текста источника, с `source`. Если живого
    факта во входе нет — поле отсутствует (НЕ выдумывать).
  - Сохранять привязку к источникам (`sources`, `quote.source`).
- **ВЫХОД:** строго JSON по §4 (валидируется схемой; при несоответствии — повтор).

## 6. Заглушки — жёсткое правило

**Пользователю НИКОГДА не показывается «информация появится позже».** Для каждого
блока: либо реальный контент (его и даёт этот проход — `verdict`, `compounds[].note`,
`lead_fact`, определения действий), **либо блок отсутствует в ответе** и клиент его
не рендерит. Пустая обещалка хуже отсутствия — она кричит «недоделано». Это
отменяет текущие `action_definition: null`, «Описание появится позже» у веществ и
`fun_fact: null`-как-заглушку.

## 7. Деньги и инкрементальность (под стабильный корпус)

- **Разовый батч:** N растений × 1 (max пара) LLM-вызовов. Ограниченный единоразовый
  расход; платим один раз за качество.
- **Хэш-гейт.** Хранить монограф с `generated_from_hash` = хэш дистиллированного
  входа. Повторный прогон батча **регенерирует только растения, у которых хэш
  изменился** → идемпотентно, новая книга бьёт по токенам лишь за затронутые виды
  (пайплайн уже знает, какие растения тронула книга — переиспользовать этот сигнал).
- **Модель:** сильная для качества; опц. дешёвая на массу + сильная на трудные/ревью.

---

## 8. Publish-gate — P0/P1 чеки (в `data_quality_findings`)

Кандидат не публикуется, пока не пройдёт:
- **P0 `ungrounded_claim`** — факт в монографе не прослеживается во входных фактах.
- **P0 `identity_conflict`** — противоречивый вердикт (`роль toxic` + `edible` без
  объяснения в `verdict`; `is_toxic` не соответствует источникам). Кейс Хмеля.
- **P1 `residual_ocr`** — остались характерные OCR-паттерны (ять/«нишек»/битые
  буквы) в видимых полях.
- **P1 `dup_not_merged`** — в `uses`/`compounds` остались очевидные морфо/синоним-дубли.
- **P1 `stub_leak`** — в видимом поле фраза-заглушка.

Первый батч — выборочный ручной просмотр поверх guard; дальше — доверие чекам.

---

## 9. Что НЕ трогаем

- **MCP `get_plant` остаётся сырым** (агентам нужна полная фактура с `original_text`
  и источниками). Двухслойность: **агентам — сырьё, людям — выверенный монограф.**
- Детерминированный скелет: ссылки на рецепты/«ещё растения», фото, ранжирование
  по числу источников, атрибуция — это вход и каркас, LLM полирует только тексты.
- Default `GET /plants/{id}` — без изменений.

---

## 10. Кросс-ссылки («ещё растения с этим действием»)

Для них нужны стабильные id действий/веществ. **Полный словарь действий A1 для
запуска НЕ обязателен:** канонизации синонимов в этом проходе + маппинга на
канонические имена достаточно, чтобы склеить ссылки. Полную консолидацию A1 можно
доделать позже как отдельную работу.

## 10.5. Согласование: два LLM-слоя и ПОРЯДОК (2026-06-10, с командой бэкенда)

Этот RFC — **Слой 2** (генерация читательского текста). Есть отдельный **Слой 1**
(`RFC-data-quality-llm.md`): LLM чинит сами ДАННЫЕ — адъюдикация находок линтера,
снос мусора (trap-карточки соль/вода/кислота уже снесены), чистка алиасов, мердж
канонических дублей, разрешение toxic/edible. **Слой 1 идёт ПЕРВЫМ** — генерировать
монограф из грязных данных = полировать мусор. Часть проблем Хмеля (морфо/синоним-
дубли действий и состава, OCR, противоречие toxic) — это классы чистки Слоя 1;
после них вход сюда уже компактный и честный.

Разделение труда:
- **Слой 1 (данные):** канонизация синонимов действий/состава (выгода и агентам),
  `identity_conflict` (toxic+edible) — добавляется в линтер рано.
- **Слой 2 (этот RFC):** cap, проза, `verdict`, `lead_fact`, OCR-полировка видимого
  текста, publish-gate генерёнышей.
- **Общий каркас:** LLM-батч по сущностям + обязательный грунтинг + кэш-по-хэшу +
  review-gate + Temporal на dispatcher-очереди. Строится один раз (находки для L1,
  растения для L2). §7-хэш-гейт и §8-publish-gate — части этого общего каркаса/линтера.

Publish-gate чеки из §8 (`ungrounded_claim`, `identity_conflict`, `residual_ocr`,
`dup_not_merged`, `stub_leak`) регистрируются как ВАЛИДАТОРЫ в общем
`data_quality_findings`-реестре (не отдельная подсистема).

## 11. Scope / non-goals

- Это **не** request-time LLM в общем случае (только опц. фолбэк). Генерация —
  пакетная, оффлайн, review-gated.
- Не переписываем источники и не добавляем знаний извне корпуса — только чистим и
  организуем то, что уже обосновано.
- Фаза 1 остаётся **детерминированной для дистилляции/ссылок/ранжирования**; новый
  слой — только текстовые поля, и они **review-gated и хранимые**, не на лету.

## 12. Открытые вопросы
1. Где хранить (новая таблица `plant_reader_monograph` vs JSON-колонка на `plant`)?
2. Cap-параметры (N действий, M групп) — подобрать на нескольких богатых видах
   (Хмель, Лопух, Крапива) так, чтобы payload влез в «десятки КБ».
3. Нужен ли человеку видимый «полный список» (133) хоть где-то, или довольствуемся
   капом + ссылкой в MCP/сырой эндпоинт для любопытных? (Гипотеза: кап достаточно.)
4. Язык бейджей при нюансном вердикте: оставляем бейджи, но согласованные с
   `verdict`, или заменяем строкой?
