# RFC: квесты-прогулки — гео/сезонная «коллекция» растений как режим приложения

Статус: **Proposed** · Автор: «Что растёт» (клиентский агент) · Создан: 2026-06-10

> Продуктовый слой ВОВЛЕЧЕНИЯ поверх ядра-определителя. Опирается на:
> определение по фото (в проде), геолокацию (в проде), `find_observations_nearby`
> (iNaturalist, MCP/планируемое обогащение), Историю наблюдений (в проде) и
> «читательский монограф» (`RFC-reader-monograph.md`) как контент-награду.
> **Эталон:** это игра для обычного человека, и она должна радовать, а не бесить.

---

## 1. Идея

Квест = маленькая **локальная сезонная коллекция** растений: «сходи и определи вот
эти виды рядом с собой». Закрыл коллекцию целиком → получил бейдж и доступ/повод
прочитать их монографы. Награда — **знание**, а не пустой счётчик.

Зачем: ядро сейчас — одноразовая утилита («встретил растение → спросил»). Квесты
дают **петлю возвращения** и причину открывать приложение снова, **усиливая** ядро,
а не конкурируя с ним.

---

## 2. Позиционирование: РЕЖИМ существующего приложения, не отдельный продукт

**Решение: одно приложение, два режима.** Квесты — отдельный опциональный раздел
(«Прогулки»/«Экспедиции»), а не форк и не геймификация повсюду.

Почему развитие:
- Квест питается ядром: определение, гео, база знаний, История — всё то же.
  Отдельное приложение = дублировать движок ради той же аудитории.
- Та же аудитория и то же хобби; сплит фрагментирует базу, листинги, ревью,
  поддержку.
- Наша архитектура (общий KMP, тонкий клиент) делает добавление раздела дешёвым.

Почему именно отдельный режим (а не «игра везде»):
- Ядро-«Определитель» должно остаться **серьёзным доверенным** инструментом (люди
  проверяют съедобность/токсичность). Геймификация поверх безопасности подрывает
  доверие.
- Home = чистое определение (как сейчас). Квесты — в своём разделе, куда заходишь
  сам. Утилитарный пользователь его не трогает.
- Это снимает безопасностное противоречие: геймифицируем **исследование**, никогда —
  **оценку безопасности** (она остаётся трезвой справкой).

Прецедент: iNaturalist вынес **Seek** в отдельное приложение, но ради приватности/
детской аудитории (без аккаунта, без шеринга гео) — у нас этих причин нет, данные и
аудитория общие. Значит «один app, два режима» уместнее сплита.

---

## 3. Что такое квест (модель)

- **Тема** (даёт смысл подборке): «Съедобные дикоросы луга», «Лекарственные травы
  июня», «Деревья парка», «Семейство крестоцветных рядом».
- **Гео-сезонный охват**: цели берутся из того, что **реально наблюдают рядом и в
  этот месяц** (см. §4) — не из всего корпуса.
- **Маленький размер**: 3–6 видов. Закрываемость важнее полноты.
- **Цели** = список видов (по `_latin_key` — мост вид↔наш монограф уже есть).
- **Награда**: бейдж + «полевой журнал» (что собрал) + доступ/повод прочитать
  монографы видов коллекции.

---

## 4. Как генерим цели (на бэке)

Серверный «движок квестов»:
1. `find_observations_nearby(lat, lng, radius)` → виды, реально наблюдаемые рядом.
2. **Фильтр по сезону**: даты наблюдений iNat = настоящая фенология; оставляем
   виды, наблюдаемые в текущем месяце в этом регионе.
3. **Фильтр по корпусу**: оставляем виды, для которых у нас есть монограф (есть что
   читать как награду) и (по теме) нужная роль/семейство/съедобность.
4. **Безопасность (§6)**: для «съедобных»-тем — только нетоксичные; токсичные — лишь
   в образовательном обрамлении.
5. **Кап сложности**: 3–6 в основном частых видов; редкие — максимум один «бонус».

Результат — динамический, достижимый, осмысленный список. Генерация на сервере;
клиент только рендерит.

---

## 5. Прогресс (почти бесплатно)

- Прогресс = матч **определений пользователя** против целей квеста по `_latin_key`.
- Источник определений — уже существующая **История** (она пишет, что определено,
  с гео/временем). Поэтому отдельного «трекинга» городить не надо: квест — это
  кураторская **витрина поверх тех же определений**.
- Засчитываем определение в квест, если: вид совпал (точно или близко — см. §8) И
  (если включено) гео/время правдоподобны.
- Закрыл все цели → бейдж + журнал.

---

## 6. Безопасность — жёсткие правила

- **Никогда не геймифицируем «найди/собери/съешь ядовитое».** Темы про съедобное
  ведут только к нетоксичным видам.
- Токсичные виды допустимы лишь в формате «научись узнавать и НЕ трогать»
  (образовательный квест-предупреждение), с явной рамкой, без «коллекционного» азарта.
- Монограф-награда сохраняет трезвую справку о токсичности/противопоказаниях
  (ядро не геймифицируется).
- Не подталкиваем к заходу в опасные места / частную территорию (формулировки целей
  нейтральные: «встреть рядом», а не «доберись до…»).

---

## 7. Field-first / офлайн

- Квест **предзагружается** (дома, на связи): цели + монографы-награды кэшируются.
- Проходится **офлайн в лесу** (определения копятся в Истории, как сейчас).
- **Синк позже**: прогресс/бейдж досчитываются при появлении связи. Переиспользуем
  офлайн-механику Истории (`retryPending`).

---

## 8. Толерантность к определению (чтобы не бесило)

- PlantNet не идеален: засчитывать **род / близкое совпадение**, а не только точный
  вид.
- Дать **ручное подтверждение** («это оно») как фолбэк, если автоматика не уверена.
- Не требовать «идеального» фото — квест про исследование, а не про точность съёмки.

---

## 9. Бэк vs клиент

- **Сервер:** движок квестов (генерация из iNat-nearby + сезон + тема + корпус +
  безопасность), хранение определений квеста, расчёт прогресса/бейджей.
- **Клиент:** раздел «Прогулки» — список доступных квестов рядом, экран квеста
  (цели + прогресс), журнал/бейджи. Тонкий: рендер + кэш, без бизнес-логики.

## 10. Эскиз данных (спека, не код)

```jsonc

{ "id":"…", "theme":"edible_meadow", "title":"Съедобные дикоросы луга",
  "season":"2026-06", "area":{"lat":…, "lng":…, "radius_km":5},
  "items":[ {"latin_key":"taraxacum_officinale","plant_id":"…","name":"Одуванчик",
             "common": true} , … ],   // 3–6 целей
  "badge":{"id":"meadow_forager_june","title":"Луговой фуражир"} }

// прогресс пользователя (выводится из Истории, не дублирует её)
{ "quest_id":"…", "matched":["taraxacum_officinale", …],
  "completed": false, "badge_earned": false }
```

## 11. Зависимости
- `find_observations_nearby` доведён до прода + умеет фильтр по месяцу (фенология).
- `RFC-reader-monograph.md` — чтобы награда-чтение была приятной (иначе «закрыл
  коллекцию» ведёт в сырой дамп).
- История наблюдений (в проде) — основа прогресса.

## 12. Scope / non-goals
- Не соревновательный режим, не лидерборды (v1 — личная обучающая игра).
- Не тяжёлый античит (v1): лёгкая сверка гео/EXIF опционально позже.
- Не социальные фичи (шеринг/друзья) — отдельный возможный слой потом.
- Ядро-определитель и его доверие — не геймифицируются.

## 13. Открытые вопросы
1. Где «живёт» прогресс — на сервере (нужен какой-то per-device ключ, у нас сейчас
   аккаунтов нет) или **локально на устройстве** (как История)? Гипотеза: локально,
   как История, — без аккаунтов; бейджи на устройстве.
2. Без аккаунта бейджи не переносятся между устройствами — это ок для v1?
3. Радиус/частота обновления квестов; как часто генерить новые.
4. Темы для старта (предлагаю: «съедобные рядом», «лекарственные этого месяца»,
   «деревья парка»).
5. Нужен ли минимальный онлайн для старта квеста (генерация) при офлайн-прохождении —
   да (предзагрузка), это ок?
