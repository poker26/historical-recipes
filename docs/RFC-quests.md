# RFC: квесты-прогулки — гео/сезонная «коллекция» растений как режим приложения

Статус: **Proposed** · Автор: «Что растёт» (клиентский агент) · Создан: 2026-06-10

> Продуктовый слой ВОВЛЕЧЕНИЯ поверх ядра-определителя. Опирается на:
> определение по фото (в проде), геолокацию (в проде), `find_observations_nearby`
> (iNaturalist, MCP/планируемое обогащение), Историю наблюдений (в проде) и
> «читательский монограф» (`RFC-reader-monograph.md`) как контент-награду.
> **Эталон:** это игра для обычного человека, и она должна радовать, а не бесить.

---

## 1. Идея

Игровой режим из двух слоёв (§3): **прогулка** «я тут → 5 растений рядом → определи
их» (локальная игровая единица) и **бейдж места×сезона** за изучение именованного
места в сезонном окне («Изучил Битцевский лесопарк в начале мая»). Прогулки — кусочки
бейджа.

**Награда — это сам бейдж, и его ценность в РЕДКОСТИ («которого ни у кого нет»).**
Информация (монограф) при этом НЕ награда и НЕ гейтится: мы отдаём её всем и всегда
— это базовый продукт. Квест ничего не «разблокирует»; он даёт статус-достижение,
эмоцию обладания редкой вещью. См. §3a про механику дефицита.

Зачем: ядро сейчас — одноразовая утилита («встретил растение → спросил»). Квесты
дают **петлю возвращения** и причину открывать приложение снова, **усиливая** ядро,
а не конкурируя с ним.

---

## 2. Позиционирование: РЕЖИМ существующего приложения, не отдельный продукт

**Решение: одно приложение, два режима.** Квесты — отдельный опциональный раздел
(«Прогулки»/«Экспедиции»), а не форк и не геймификация повсюду.

Почему развитие:
- Квест питается ядром: определение, гео, база знаний, История — всё то же.
  Отдельное приложение = дублировать движок ради той же аудитории.
- Та же аудитория и то же хобби; сплит фрагментирует базу, листинги, ревью,
  поддержку.
- Наша архитектура (общий KMP, тонкий клиент) делает добавление раздела дешёвым.

Почему именно отдельный режим (а не «игра везде»):
- Ядро-«Определитель» должно остаться **серьёзным доверенным** инструментом (люди
  проверяют съедобность/токсичность). Геймификация поверх безопасности подрывает
  доверие.
- Home = чистое определение (как сейчас). Квесты — в своём разделе, куда заходишь
  сам. Утилитарный пользователь его не трогает.
- Это снимает безопасностное противоречие: геймифицируем **исследование**, никогда —
  **оценку безопасности** (она остаётся трезвой справкой).

Прецедент: iNaturalist вынес **Seek** в отдельное приложение, но ради приватности/
детской аудитории (без аккаунта, без шеринга гео) — у нас этих причин нет, данные и
аудитория общие. Значит «один app, два режима» уместнее сплита.

## 3. Что такое квест — ДВА СЛОЯ

**Слой 1 — Прогулка (локальная игровая единица).** Сценарий: «я тут» (GPS) → берём
**5 видов, реально наблюдаемых рядом** → показываем **5 карточек** → фотографируешь и
определяешь каждую (переиспользуем определение + Историю) → «прогулка пройдена».
- Размер: **5 карточек** (3–6).
- **Корпус НЕ обязателен.** Вид, которого у нас нет, всё равно карточка: показываем
  имя/фото из iNat, определение засчитывается (как «нет в БД» в результатах
  определения — уже умеем). Монограф — бонус, когда он у нас есть.
- Цели матчатся по `_latin_key`.
- Тема — опциональная «приправа» прогулки, НЕ обязательный выбор (минимум вопросов,
  §8a): по умолчанию просто «5 рядом».

**Слой 2 — Бейдж места×сезона (редкий, «которого ни у кого нет»).** Не за одну
прогулку, а за **изучение именованного места в сезонном окне**: «Изучил Битцевский
лесопарк в начале мая», «Подмосковный лес в первой половине июня». Локальные прогулки —
кусочки этого набора. См. §3a.

Монографы доступны всегда, вне зависимости от квестов — информация не гейтится.

---

## 3a. Бейдж места×сезона — ядро ценности («которого ни у кого нет»)

Бейдж радует, только если эксклюзивен. Главный механизм — **именованное место ×
сезонное окно**, и дефицит создаёт сама природа, а не искусственный таймер:

- **Место — именованное и узнаваемое**, любой масштаб: от конкретного парка
  («Битцевский лесопарк») до большой зоны («Подмосковный лес»). Границы берём из
  **OpenStreetMap** (парки/лесопарки/заповедники — размеченные полигоны с именами).
  GPS-точка → накрывающее именованное место.
- **Окно — сезонный срез** («начало мая»), под фенологию.
- **Что закрывать** — характерный набор видов места×окна: агрегированные наблюдения
  iNat **внутри полигона** за это окно → топ частых узнаваемых видов. Локальные
  прогулки — кусочки этого набора.
- **Бейдж** — когда определил достаточную долю набора в пределах окна (порог — §13).
- **Дефицит** — окно закрылось → бейдж залочен НАВСЕГДА. «Битцевский · начало мая
  2026» в июне уже не получить. Это редкость, которую создаёт фенология (данные iNat,
  которых нет у обычных определителей) — честно и уникально наше.
- **Коллекционность** — десятки мест × сезонов = стена достижений; локальный
  патриотизм («знаю свой парк») вовлекает.

Вторичные механизмы дефицита: сложность набора, «первые N закрывших», стрики.

Вложенность мест (Битцевский ⊂ Москва ⊂ Подмосковье): бейдж вешаем на **самое
конкретное накрывающее место**; широкие зоны — отдельные мета-достижения (§13).

Хранение/показ (§8a, §13): факт выдачи редкого бейджа фиксирует **сервер** (штамп
окна, порядковый номер) — без аккаунтов, по ключу устройства. Показуемость: полка
бейджей + экспорт картинки-карточки. Иначе «ни у кого нет» не с чем сравнивать.

## 4. Как генерим (на бэке)

**Прогулка («5 рядом»):**
1. GPS → `find_observations_nearby(lat, lng, radius)` → виды, наблюдаемые рядом.
2. Фильтр: **частые** (по числу наблюдений) ∩ **узнаваемые по фото** (исключаем мхи /
   злаки / неотличимую телефоном мелочь). **Корпус — НЕ фильтр** (нет монографа — ок).
3. (Опц.) фильтр по теме; безопасность (§6) для «съедобных»-тем — только нетоксичные.
4. Берём **топ-5** по встречаемости.

**Характерный набор места×окна (для бейджа):**
1. GPS → **OSM-полигон** накрывающего именованного места (парк/лесопарк/зона).
2. Агрегируем наблюдения iNat **внутри полигона × сезонное окно** → топ-K частых
   узнаваемых видов = «набор места».
3. Бейдж — при покрытии порога (§13) до закрытия окна.

Вся генерация и геопространственная агрегация — на сервере; клиент только рендерит.

---

## 5. Прогресс (почти бесплатно)

- Источник истины — уже существующая **История** (пишет, что/где/когда определено).
  Отдельного трекинга не городим; квест — **витрина поверх тех же определений**. Матч
  по `_latin_key` (точно/близко — §8).
- **Прогулка** закрыта, когда определены её 5 карточек.
- **Бейдж места×сезона** — накапливаем РАЗЛИЧНЫЕ виды из «набора места», определённые
  **внутри полигона за окно**; достиг порога → сервер выдаёт бейдж (штамп окна, #N).
  Прогресс считается локально (из Истории), выдачу фиксирует сервер (§8a).

---

## 6. Безопасность — жёсткие правила

- **Никогда не геймифицируем «найди/собери/съешь ядовитое».** Темы про съедобное
  ведут только к нетоксичным видам.
- Токсичные виды допустимы лишь в формате «научись узнавать и НЕ трогать»
  (образовательный квест-предупреждение), с явной рамкой, без «коллекционного» азарта.
- Монограф-награда сохраняет трезвую справку о токсичности/противопоказаниях
  (ядро не геймифицируется).
- Не подталкиваем к заходу в опасные места / частную территорию (формулировки целей
  нейтральные: «встреть рядом», а не «доберись до…»).

---

## 7. Field-first / офлайн

- Квест **предзагружается** (дома, на связи): цели + монографы-награды кэшируются.
- Проходится **офлайн в лесу** (определения копятся в Истории, как сейчас).
- **Синк позже**: прогресс/бейдж досчитываются при появлении связи. Переиспользуем
  офлайн-механику Истории (`retryPending`).

---

## 8. Толерантность к определению (чтобы не бесило)

- PlantNet не идеален: засчитывать **род / близкое совпадение**, а не только точный
  вид.
- Дать **ручное подтверждение** («это оно») как фолбэк, если автоматика не уверена.
- Не требовать «идеального» фото — квест про исследование, а не про точность съёмки.

---

## 8a. Идентичность пользователя — unattended, без вопросов (РЕШЕНО)

Базовые допущения (заданы владельцем): **(1) пользователь редко меняет устройство;
(2) чем меньше вопросов, тем лучше.** Из них — максимально молчаливая модель.

Регистрация нулевая: никаких email/SMS/кодов и **никакого экрана регистрации**.
**НЕ использовать IMEI / железные id** — iOS их не даёт никогда, Android заблокировал
с v10, + нарушение privacy-политики App Store.

Механика:
- При первом запуске клиент генерирует случайный **UUID-ключ устройства** и **молча**
  регистрирует его на сервере (POST ключа → запись). Пользователь ничего не вводит.
- Ключ хранится в защищённом, переживающем переустановку месте: **iOS — Keychain**
  (переживает удаление приложения; iCloud-синк → переезд на новый айфон того же Apple
  ID); **Android — Block Store** (бэкап в Google + перенос при restore).
- **Свой UUID, а не IDFV/ANDROID_ID** — у тех семантика сброса не в наших руках.
- **Ника НЕ спрашиваем** (минимум вопросов). Бейдж принадлежит устройству и
  показывается на личной полке с **порядковым номером + датой** — этого хватает для
  «которого ни у кого нет», имя не нужно. Захочет подписать — задаст в **настройках**
  сам; мы не прерываем вопросом.
- **Кода восстановления в v1 нет** (допущение «редко меняет устройство»): полагаемся
  на нативный синк (iCloud Keychain / Block Store restore). Лишнюю фичу не плодим.

Компромиссы (приемлемы для НЕсоревновательных бейджей): ключ сбрасывается при
переустановке на устройстве без бэкапа / factory reset → бейджи теряются (редкий
случай, митигируется нативным синком); лёгкий «фарм» через переустановку возможен —
тяжёлый античит не нужен. Privacy чистая: случайный UUID без PII, без трекинга.

> **Принцип UX (общий для всего приложения):** всё silent/auto; опции живут в
> настройках; пользователя НЕ прерываем вопросами. Касается и квестов — не «выбери
> тему», а просто показываем доступные рядом.

## 9. Бэк vs клиент

- **Сервер:** движок прогулок (iNat-nearby + частые ∩ узнаваемые), геопространственная
  агрегация набора места×окна (OSM-полигон × iNat × сезон) и **выдача бейджей**
  (проверка окна, штамп, порядковый номер — то, что делает дефицит настоящим).
- **Клиент:** раздел «Прогулки» — прогулки рядом (5 карточек), экран прогресса, полка
  бейджей/журнал, экспорт карточки. **Прогресс считает локально** (матч Истории); по
  достижении порога — запрашивает у сервера выдачу бейджа.

## 10. Эскиз данных (спека, не код)

```jsonc
// ПРОГУЛКА — «5 рядом» под текущую точку (Слой 1)
{ "id":"…", "kind":"walk", "near":{"lat":…, "lng":…},
  "items":[ {"latin_key":"taraxacum_officinale","name":"Одуванчик",
             "inat_photo":"…", "plant_id":"…|null"} , … ] }  // plant_id null = нет монографа, ОК

// ЦЕЛЬ-БЕЙДЖ места×окна (Слой 2) — определяет «набор места» и дефицит
{ "id":"bitsa_2026_may_early", "kind":"place_badge",
  "place":{ "osm_id":"relation/123", "name":"Битцевский лесопарк" },  // граница из OSM
  "window":{"from":"2026-05-01","to":"2026-05-15"},   // закрывается → больше не выдать
  "species_set":["…latin_key…", …],                   // характерный набор (iNat∩полигон∩окно)
  "threshold": 0.6 }                                  // доля набора для бейджа (§13)

// ПРОГРЕСС — локально на устройстве (из Истории), сервер не нужен
{ "badge_id":"bitsa_2026_may_early", "matched":["…", …] }

// ВЫДАННЫЙ бейдж — фиксирует СЕРВЕР (дефицит + показуемость). Ника нет (§8a).
{ "badge_id":"bitsa_2026_may_early", "device_key":"…",
  "issued_at":"2026-05-12T…", "ordinal": 37,   // «ты #37»
  "window_closed": true }                       // окно закрыто → больше никому
```

## 11. Зависимости
- `find_observations_nearby` доведён до прода + фильтры по месяцу (фенология) и по
  полигону (наблюдения внутри границы места).
- **OpenStreetMap** — границы именованных мест (парки/лесопарки/заповедники как
  полигоны) + lookup «точка → накрывающее место». Можно через Overpass API /
  предзагруженный экстракт по региону.
- `RFC-reader-monograph.md` — чтобы монограф-бонус был приятным (но он НЕ гейтит
  квест — корпус необязателен, §3/§4).
- История наблюдений (в проде) — источник прогресса.

## 12. Scope / non-goals
- Не соревновательный режим, не лидерборды (v1 — личная обучающая игра).
- Не тяжёлый античит (v1): лёгкая сверка гео/EXIF опционально позже.
- Не социальные фичи (шеринг/друзья) — отдельный возможный слой потом.
- Ядро-определитель и его доверие — не геймифицируются.

## 13. Открытые вопросы
> Решено: идентичность (§8a, unattended UUID); место = именованное из OSM, бейдж на
> самое конкретное накрывающее место (§3a); корпус не обязателен (§3/§4).

Остаются «ручки» бейджа места×сезона:
1. **Гранулярность окна** — половинки месяца? «ранний/средний/поздний» месяц? Под
   фенологию региона.
2. **Порог** — какая доля «набора места» = бейдж (предлагаю 60–70%: достижимо, но не
   тривиально). И как считать «набор» (топ-K по встречаемости внутри полигона×окна).
3. **Вложенные места** — выдаём только на самое конкретное (парк), а широкие зоны
   («Подмосковный лес») — отдельным мета-достижением; когда добавлять второй уровень.
4. Радиус «5 рядом» для прогулки; как часто обновлять прогулки.
5. Минимальный онлайн для генерации (прогулка/набор) при офлайн-прохождении — да
   (предзагрузка дома), это ок?
