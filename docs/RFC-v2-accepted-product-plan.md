# RFC v2.0 «Что растёт» — принятый план: ядро, прогулки, аналитика, пуши, витрина базы

**Статус:** Accepted 2026-08-24 (владелец продукта + Claude)
**Заменяет:** продуктовую композицию из `RFC-mobile-product-social-walks-analytics.md`
(тот документ остаётся источником полного словаря аналитики §14 и дизайн-чеклистов §21;
его presence-слой, роутинг-движок и процесс трёх концепций в v2.0 НЕ входят — см. §9).
**Реализация:** бэкенд и клиентская обвязка — сразу; вёрстка экранов — после утверждения
карты экранов и дизайн-направления (§8).

---

## 1. Что уже сделано (факты, не планы)

Эти решения задеплоены на прод 2026-08-24 и являются фундаментом v2.0:

1. **Кумулятивная модель «Знаток места»** — значок места один (`badge_id = {place_id}:all`),
   ярусы навсегда, прогресс не сгорает на смене месяца. Пул места = объединение всех
   сезонных наборов. Сезонное окно — только витрина «что искать сейчас» (`place_set`).
   Старые оконные значки мигрированы. Кастом-квесты сохраняют правило «новый квест —
   новый поиск» (зачёт с момента создания).
2. **`GET /api/quests/claimable`** — все заработанные-незабранные значки девайса одним
   вызовом (места + биотопы).
3. **`quest_credit` в ответе `POST /api/identify`** — «снимок зачтён в прогулку X, N из M»
   прямо в результате определения.
4. Клиент (не выложен): плашка квест-кредита в результате, баннер «Ты заработал значок —
   забери» на главной (Android; iOS-зеркало — в v2.0).
5. Биотопные значки всегда были кумулятивными и зачитываются без запуска квеста —
   принцип «прогресс следует за действием» уже работает на сервере целиком.

Следствие для терминологии: **walk_instance (сессия прогулки) ≠ значок (мастерство места)**.
Сессия — «когда гуляли и с кем», новая сущность v2.0. Мастерство — кумулятивный значок,
уже в проде. Сессии живут ПОВЕРХ мастерства и никогда не сбрасывают его.

## 2. Цель v2.0 одним абзацем

Camera-first ядро без конкурирующего шума; после ответа — честное объяснение и видимый
прогресс; прогулки как понятный способ провести время (в т.ч. с другом по ссылке);
база знаний вынесена на витрину, а не спрятана за удачным определением; каждый экран
измерим с первого дня; пуши доносят заработанное и сезонное. Всё — одним релизом 2.0
(RuStore + App Store), без промежуточных выкладок.

## 3. Информационная архитектура (принято из драфта, без изменений)

Нижняя навигация: **Определить · Прогулки · Коллекция**. Профиль — через аватар в шапке.
Правило контекста: детальный экран знает `entry_point` и меняет вторичное действие.
Термин «Квесты» в UI умирает, живёт «Прогулки» (в API `quest*` остаётся).

Отличие от драфта — **витрина базы**: вкладка «Определить» ниже камеры несёт сезонную
полку «Сейчас в лесу» (§6), а не только последние находки. Обоснование: 90% открывших
карточку идут в рецепты/состав — контент-вовлечение сильнейшее в приложении, но у него
нет входа, кроме удачного определения.

## 4. Аналитика (first-party, решено)

Решения по открытым вопросам драфта: **Q17 = свой контур** (Postgres + Grafana, данные в
РФ, объём ~100 тыс. событий/мес — тривиален), **Q19 = raw 90 дней** + дневные агрегаты,
**Q20 = координатных heatmap НЕТ** (на нашей аудитории — шум; семантические `element_id`
дают всё), **Q18** — обезличенная продуктовая аналитика без ПД, покрывается политикой
конфиденциальности (privacy-label уже поданы, дописать пункт).

- Контракт: `POST /api/analytics/events/batch` (schema_version, идемпотентные event_id),
  таблица `product_events` (см. драфт §15.3). Whitelist в flora-nginx.
- `analytics_device_id` = отдельный псевдоним (uuid, генерится клиентом, НЕ device_key,
  НЕ handle).
- Клиент: bounded-очередь в KMP commonMain, батч-отправка, offline-first, сбой телеметрии
  никогда не ломает сценарий.
- Сессия = cold start или возврат после 30 мин фона. `screen_viewed`/`screen_left` c
  `active_ms`, cap на интервал.
- Словарь событий = драфт §14.4–14.10 минус координатные heatmap (§14.11.C), минус
  события presence (§14.10 частично). `screen_id`/`element_id` фиксируются на карте
  экранов ДО вёрстки; `layout_version=1` — текущий клиент, `2` — редизайн (даёт
  сравнение до/после).
- Dashboards (Grafana, той же инсталляции): воронка определения, пути экранов,
  секции карточки, воронка прогулок, конструктор, до/после layout_version.

## 5. Пуши (новое — в драфте отсутствовали)

Без пушей социальный и наградный слой — письмо без почтальона (доказано: «Мастер»
Легчищево висел незамеченным; claimable-значки молчат).

- **iOS:** APNs напрямую с бэкенда (HTTP/2, токен-ключ .p8 из dev-портала — действие
  владельца, один раз). Проверить достижимость `api.push.apple.com` с server 1; если
  резана — через trusttunnel.
- **Android:** RuStore Push SDK (VK-инфраструктура, без Google). Включение проекта в
  консоли RuStore — действие владельца; SDK + сервис в клиенте — наши.
- **Бэкенд:** таблица `push_tokens (device_key, platform, token, updated_at)` +
  `POST /api/devices/{key}/push-token` + отправлялка с ретраями и чисткой мёртвых токенов.
- **Первые пуши (только ценность, никакого спама):**
  1. «Ты заработал значок „{tier} · {место}" — забери» (по claimable, не чаще 1/сутки);
  2. «В {место} новый сезонный список — {N} видов, {M} из них ты ещё не находил»
     (при смене месяца, только по местам с прогрессом девайса);
  3. «{друг} зовёт тебя на прогулку в {место}» (walk-приглашение, §7).
- Тумблер в настройках; дефолт — включено с системным разрешением.

## 6. Витрина базы: «Сейчас в лесу» (новое)

Сезонная контентная полка — вход в УТП без фотоаппарата:

- `GET /api/showcase/seasonal?lat&lng` → 5–8 карточек «что сейчас можно встретить рядом
  и зачем оно»: фото, имя, **крючок из монографа** (lead_fact/verdict — одна живая
  фраза, не «полезное растение»), бейджи «съедобно/лекарственное/осторожно», счётчик
  рецептов. Строится из nearby-слоя ∩ корпус, ранжирование: в корпусе > с монографом >
  частота в этом месяце.
- Тап → карточка растения (`entry_point=showcase`), там уже работают рецепты/состав.
- Полка живёт на «Определить» ниже камеры и заменяет чистый «последние находки»
  (находки уезжают в Коллекцию, где им место).
- Требование к качеству: без пустых состояний — нет гео → полка по сезону страны;
  скучный крючок хуже отсутствия карточки (капы и фильтры на текст).

## 7. Прогулки v2.0

### 7.1. Хаб «Прогулки»
Три входа (из драфта §10.4): «Что растёт рядом» (свободное исследование + биотоп),
«Найти прогулку» (места с наборами), «Создать маршрут» (конструктор области). Плюс:
активная/незавершённая сессия и приглашения. Лидерборд уезжает в профиль; таб «сезон»
лидерборда удаляется (после кумулятива пуст навсегда).

### 7.2. Сессия прогулки (walk_instances) и приглашение друга
Единственная социальная механика v2.0 — **позвать друга по ссылке** (свою плотность
юзер приносит сам; presence незнакомцев вырезан — см. §9).

- `walk_instances(id, kind prepared|custom, quest_place_id, owner_device_key,
  planned_at, started_at, ended_at, status, visibility)`;
- `walk_participants(walk_instance_id, device_key, role, joined_at, status)`;
- `POST /api/walks` (создать) · `GET /api/walks/{id}` (публичный предпросмотр без
  координат участников) · `join / start / finish` · `GET /api/walks/{id}/progress`
  (вклад участников: distinct-виды по каждому, из identifications внутри полигона
  за время сессии);
- ссылка `botanik.fun/walk/{id}` (App Links/Universal Links уже настроены на домене);
- личная находка всегда в коллекции автора; сессия только агрегирует;
- сессия НЕ обязательна: свободное исследование и значки работают без неё.

### 7.3. Конструктор кастомной прогулки — геометрия без роутинга
Из драфта берётся UX области (§12.1–12.6): карта — главный элемент, drag-ручка радиуса +
плавный контрол, круг ≠ маршрут, никаких кнопок 0.5/1/2 км. НЕ берётся Ступень B
(построение пути по дорожной сети) — отдельный RFC после данных (§9).

- **`POST /api/quests/custom/estimate`** (дешёвая оценка до генерации): viability
  ready|sparse|unavailable, candidate/confirmed/expected counts, min_viable_radius_km,
  suggested_radius_km, биотопы. Дебаунс на клиенте, кэш по geohash+радиус+месяц.
- Расширение области — только с согласия юзера (кнопка, не молча).
- Радиус свободный в серверном диапазоне (0.3–10 км пешком для старта); «вело» в v2.0 =
  пресет большего радиуса с честной подписью, не отдельный режим.
- Генерация — существующий `custom/create` (переиспользует всё построенное).

### 7.4. Прогресс и награда — уже работают
Кумулятивные значки, claimable-баннер, quest_credit в результате определения — §1.
Клиентская задача v2.0 — показать их по драфту §10.8/§11.3 (награда не выше следующего
полезного действия; компакт «Лес · 7/15 до Любителя» после основного ответа).

## 8. Дизайн-процесс (сокращён против драфта)

Вместо трёх полных концепций × 14 сценариев:

1. **Карта экранов и переходов** в 4 сквозных сценариях (драфт §28) + фиксация
   `screen_id`/`element_id` — обязательный гейт до вёрстки.
2. **Одно направление** — развитие начатой «Living Collection» (палитра Atlas, serif,
   герой-карточки), а не бейк-офф с нуля.
3. **Три варианта оформления только для трёх решающих экранов**: Home «Определить»,
   результат определения, хаб «Прогулки». Сравнение на одинаковом контенте.
4. Дизайн-чеклист доступности = драфт §21 (без изменений).

## 9. Вырезано из v2.0 (North Star, не сейчас)

| Что | Почему | Когда вернуться |
|---|---|---|
| Presence «кто гуляет сейчас», join-request'ы | При ~20 WAU экран вечно пуст; повтор ошибки «значки раньше гуляющих» | Когда прогулки-с-другом покажут живую плотность |
| Роутинг-движок (пути по дорожной сети) | OSRM/Valhalla + тропы РФ + ответственность за «безопасный маршрут» — дорого, ценность не доказана | Отдельный RFC, когда аналитика покажет «тесно в круге» |
| Вело как отдельный режим | Реальная разница — в роутинге, которого нет | Вместе с роутингом |
| Координатные tap-heatmap | Шум на нашей аудитории | ClickHouse-эра, если наступит |
| Три полные дизайн-концепции | Стоимость артефактов > стоимости решения | — |
| Групповой чат, аккаунты, session replay | Не-цели драфта, подтверждаем | — |

## 10. Решения по открытым вопросам драфта

Q1 поиск на Home — вторичное действие (15 запросов/нед). Q2 явный режим свободной
прогулки — нет, зачёт и так автоматический. Q3 кастом-premium — НЕ в v2.0 (сначала
устойчивое прохождение). Q5 вид в нескольких биотопах — зачёт в каждый (уже так).
Q7 тиры — биотоп-зависимые лестницы уже в коде. Q8 — радиус первичен, длительность
подписью-оценкой. Q11 — без роутинга вопрос снят. Q13–16 — presence вырезан; для
walk-сессий: видят участники по ссылке, роль owner есть, публикация находок общим
тумблером activity_public (уже в проде). Q17–20 — §4.

## 11. Фазы реализации

- **Phase A (не ждёт дизайна):** аналитика бэкенд+клиентская очередь · пуш-бэкенд +
  RuStore SDK в клиенте + APNs-проба · `custom/estimate` · `walk_instances` API ·
  `showcase/seasonal` API · iOS-зеркало claimable-баннера · снос таба «сезон».
- **Phase B (дизайн-гейт):** карта экранов → 3 варианта 3 экранов → выбор.
- **Phase C:** вёрстка v2.0 по выбранному направлению (Home/результат/карточка/хаб/
  конструктор/коллекция/профиль), `layout_version=2`.
- **Phase D:** прогон, скриншоты, «что нового» (plain-text!), RuStore + App Store
  (Codemagic), пуш-ключи в проде.

## 12. Критерии приёмки

Берутся из драфта §24 с правками: из §24.3 исключены пункты про длину пути (роутинга
нет), §24.4 сокращён до «приглашение открывает прогулку, личное ≠ групповое, лента без
точных координат». Добавлено: полка «Сейчас в лесу» не показывает пустых состояний и
мусорных крючков; пуш «забери значок» доставляется на обеих платформах; сравнение
layout_version 1→2 доступно в Grafana.
