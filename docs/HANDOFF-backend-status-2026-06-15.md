## 1. НОВОЕ И ВАЖНОЕ ДЛЯ КЛИЕНТА: `?view=field` теперь может отдавать ВЫВЕРЕННЫЙ монограф

Построен **Слой 2** (`RFC-reader-monograph`): предрасчётный, grounded, review-gated
читательский монограф. Поведение `GET /api/plants/{id}?view=field`:

- **Если для растения опубликован монограф** (`reviewed=true`) → отдаётся ОН: капнутый
  (топ-12 действий / топ-15 групп состава вместо 133/48), человеческая проза, **без
  заглушек**. Сейчас опубликовано **2 вида** (Хмель `fb743008-…`, Чистотел
  `10a42f86-…`) — на них и проверяй новый рендер.
- **Если не опубликован** → как раньше: детерминированная агрегация (обратная
  совместимость, ничего не ломается).

**[ДЕЙСТВИЕ КЛИЕНТА]** Поддержи новые поля (все опциональны, отсутствие = не рендерить):
```jsonc
{
  "verdict": "одна честная фраза (решает кейс съедобно+ядовито Хмеля)",
  "lead_fact": { "text": "живой факт", "source": "книга" },   // = бывший fun_fact, теперь реальный
  "uses": [ { "action","summary":"человеческая фраза","indications":[],
              "quote":{"text","source"}, "source_count" } ],   // ≤12, синонимы слиты
  "compounds": [ { "group","note":"короткое «что это»" } ],     // ≤15, было compound_groups
  "cautions": { "text":"одна формулировка", "toxic_parts":[] },
  "uses_total": 138, "compounds_total": 49,   // «ещё N» — полный список в RAW/MCP, если нужно
  "verdict"…, "roles":[…], "is_toxic":bool,
  "reviewed": true, "model": "qwen3-235b"
}
```
Это **ОТМЕНЯЕТ заглушки**, о которых ты спрашивал: `action_definition:null` и
`fun_fact:null` у опубликованных видов заменены реальными `compounds[].note` /
`lead_fact`. Для НЕопубликованных пока остаётся старая агрегация (с null-ами) —
постепенно заместится по мере раскатки.

- **Раскатка на все виды** — пакетно, после завершения чистки данных Слоя 1 (генерить
  из ещё-грязных карточек = полировать мусор). Сейчас опубликована пилотная пара;
  массовый прогон `ReaderMonographWorkflow` готов, ждёт Слой-1.
- **MCP `get_plant` и default-view остаются СЫРЫМИ** (агентам нужна полная фактура) —
  двухслойность не меняется.

## 2. Квесты — walk работает (но СЕЙЧАС деградирован), бейджи ждут предрасчёт

- **Контракт стабилен и подтверждён** — см. `HANDOFF-quests-backend-response.md`
  (формы places/at, badge/progress, badges; окно-канон `first-half-06`).
- **Фикс:** `POST /api/devices/register?device_key=…` теперь принимает `device_key`
  **query-строкой** (был баг — ждал в теле, твой вызов падал бы 422). Готово на проде.
- **⚠️ ВРЕМЕННО:** `GET /api/quests/walk` может отдавать `items:[]` — фоновая чистка
  данных сейчас выжирает rate-limit iNat (429). Это пройдёт, когда чистка закончит
  iNat-фазу. Код walk не менялся; на чистом iNat отдаёт 5 видов как прежде. Если в
  QA видишь пустой walk — это известно, не клиентский баг.
- **Бейджи (место×сезон)** ждут предрасчёт `species_set` по местам×окнам
  (`QuestSetBuilderWorkflow`). Он тоже iNat-тяжёлый → запускается ПОСЛЕ iNat-фазы
  чистки. До тех пор `badge/progress` отдаёт `set_size/target`, но наборы посчитаны
  только для уже прогнанных мест (Битца есть). Места Москвы (333) заингещены.

## 4. Что блокирует прогресс (чтобы ты понимал тайминг)
Единственный общий блокер сейчас — **чистка данных Слоя 1** (идентичность растений:
латынь/имена) + **rate-limit iNat** (один на всех: чистка, walk, set-builder).
Пока Слой 1 не дочищен и iNat занят: (а) массовый монограф не раскатывается, (б)
walk периодически пустой, (в) предрасчёт наборов бейджей отложен. Идентичность —
фундамент, на котором стоит и монограф, и матч квестов по `_latin_key`.

## TL;DR для тебя
1. Готовь рендер нового `?view=field` (verdict/lead_fact/uses[].summary/compounds[].note/
   cautions/«ещё N») — проверяй на Хмеле и Чистотеле.
2. Заглушек у опубликованных монографов больше нет.
3. walk может быть временно пустым (iNat 429) — не баг клиента.
4. register — теперь query-параметр.
5. Бейджи и массовый монограф — после чистки Слоя 1.
