# RFC: Гранулярность ссылок — родовой слой и маршрутизация по доменам

Статус: draft (для нас самих, не в проде — потолок качества = «пока не нравится»)
Дата: 2026-06-18
Связано: [мастер-план чистки], RFC-data-quality, RFC-reader-monograph, домен веществ
(reference-normalizer), `plant_matching.py`, `compounds.parent_id`.

## 1. Проблема

Строка рецепт-ингредиента — это **ссылка** на сущность. У ссылки есть уровень
специфичности, и он не обязан совпадать с гранулярностью корпуса:

- **специфичная** — «войлочная вишня», «корень валерианы» → один вид. ОК.
- **родовая/недоопределённая** — «вишня», «соль», «солод» → автор назвал
  категорию, а в корпусе под ней N конкретных сущностей.

Матчер обязан вернуть один `plant_id` и возвращает. Для родовой ссылки это:

1. **Детерминированно-первая, не «случайная».** Общий noun-key `вишн` через
   `setdefault` достаётся той карточке, что пришла из БД первой. Выглядит как
   рандом, по сути — произвол порядка индексации.
2. **Ложная точность.** Рецепт сказал «вишня вообще» — мы утверждаем «именно
   войлочная».
3. **Загрязнение видовых монографов.** «войлочная вишня применялась в рецепте X»,
   хотя автор писал просто «вишня». Видовая карточка набирает чужие рецепты.

Соль (вчерашний денилист) — частный случай. То же самое с «вишня», «слива»,
«солод», «лук», «полынь», «перец», «купорос»…

## 2. Это не один класс, а четыре

Расцепление — ключ к тому, чтобы не строить один мега-фикс:

| Подкласс | Пример | Природа | Лечение |
|---|---|---|---|
| **A. Чужой домен** | соль, вода, сахар | вообще не растение | денилист (СДЕЛАНО) → домен веществ |
| **B. Истинно родовая** | вишня, лук, полынь | реальный таксон, ≥2 вида в корпусе | **родовой слой (этот RFC)** |
| **C. Производное/препарат** | солод, мука, настойка | продукт переработки источника | разрешать по уточнению-источнику |
| **D. Народный самозванец** | «жидовская вишня» = физалис | чужой вид в фолк-имени рода | чинится латынью «даром» (см. 4.2) |

A нельзя лечить как B (вишня — настоящее растение, её не «запретишь»).
B нельзя лечить как A.

## 3. Принцип

**Линковать на том уровне, который named ссылка.** Специфичная → вид. Родовая
→ род. Сейчас всё тащим на уровень вида — отсюда и ложная точность, и
загрязнение. Совпадение уровня ссылки и уровня узла — единственное инвариантное
правило этого RFC.

## 4. Архитектура

### 4.1 Иерархия как у `compounds`

У `Compound` уже есть `parent_id` (класс «флавоноиды» → конкретный «рутин»).
Команда уже выбрала этот паттерн для химии. Зеркалим в растениях:

- `plants.rank` ∈ {`genus`, `species`} (default `species`; существующие строки —
  виды).
- `plants.parent_id` (вид → его родовая строка; NULL у видов без рода и у самих
  родов).

Членство и drill-down — бесплатно из `parent_id`. Монограф, MCP, фото, квесты —
всё работает на тех же строках; новый тип сущности НЕ нужен.

### 4.2 Сборка рода: русский токен группирует, латынь валидирует

**Важно:** латинский род ГРУБЕЕ народной категории. Prunus = вишня + слива +
черёмуха + абрикос + миндаль + черешня. Рецепт «вишня» ≠ «слива». Поэтому:

- **Группирует — русский noun-токен.** Члены = виды корпуса, чьё русское имя
  после съёма part-words сводится к одному и тому же noun-стему («войлочная
  вишня», «степная вишня», «вишня обыкновенная» → стем `вишн`). Переиспользуем
  `_identity` (noun=род, adj=эпитет) из `plant_matching.py`.
- **Латынь — валидатор/чистильщик.** У собранных по токену членов смотрим
  распределение латинских родов:
  - есть доминирующий латинский кластер → это и есть род; члены вне кластера —
    кандидаты в самозванцы (D), исключаются из узла. *(11 видов Cerasus + 1
    Physalis → узел = 11; физалис «жидовская вишня» вылетает по латыни — даром,
    без отдельного чека contamination.)*
  - доминирующего нет, несколько равных латинских родов → токен **много-родов**
    (см. 4.3, случай c). *(перец = Piper + Capsicum + Polygonum.)*

Так слива и вишня — РАЗНЫЕ родовые узлы (токены `слив`/`вишн`), хотя оба латинский
Prunus: латынь не форсит слияние, она лишь валидирует когерентность и кидает
импостеров.

Идентичность родового узла: `rank=genus`, `name` = русский родовой токен
(каноничная форма «Вишня»), `name_latin` = латинский род/подрод доминирующего
кластера («Cerasus»/«Prunus»). Ключ идемпотентности сборки = (rank=genus, токен).

### 4.3 Типология разрешения голого родового токена

Для токена с ≥2 различными видами в корпусе:

- **(a)** → один доминирующий латинский род, ≥2 вида → **родовая карточка**, линк
  туда. *(вишня→Cerasus)*
- **(b)** → один род, 1 вид → линк прямо на этот вид (неоднозначности нет;
  родовую строку НЕ плодим — роды только при ≥2). 
- **(c)** → несколько равных латинских родов → **NULL + флаг «ambiguous-generic»**;
  специфичные формы («чёрный перец»→Piper, «водяной перец»→Polygonum) всё равно
  разрешаются через эпитет. Опц.: отдавать disambiguation-set.
- **(d)** → латыни нет (фолк-онли) → fallback/NULL + флаг.

Импостер (D, исключить) vs легит-много-родовость (c, держать раздельно)
различаются доминированием: явный мажор + одиночный чужой латинский род = D;
несколько сопоставимых кластеров = c. Спорные уходят в review-очередь (юзеров
нет, гоняем пока не нравится).

### 4.4 Хаб без собственных фактов (решено)

Родовая строка НЕ хранит первичных `plant_*` фактов (не изобретаем данные). Вид
карточки **агрегирует факты членов с атрибуцией**: «противовоспалительное — у
войлочной и степной вишни [источник]». Reader-монограф рода = этот union-вид.

### 4.5 Куда указывают родовые рецепт-линки

`recipe_ingredient.plant_id` родового упоминания = id родовой строки. Рецепты,
сказавшие «вишня», ЧЕСТНО принадлежат роду — родовая строка владеет ими (но не
ботаническими фактами). Видовые монографы при этом очищаются от чужих рецептов.

Специфичное всегда бьёт родовое: матчер сначала пытается вид (noun+epithet), и
только голый родовой токен уходит на род. Это прямое расширение нынешних тиров.

## 5. Маршрутизация по доменам

- **Растения (B)** → родовой слой (этот RFC).
- **Вещества (A)** → денилист уже убрал из растений; внутри веществ иерархия
  `compounds.parent_id` УЖЕ есть: «соли» — класс, конкретные (поваренная,
  глауберова, калиевая) — дети. Свойства урановой ≠ поваренной — именно поэтому
  класс-родитель, а не общий лист. Растительные роды для веществ НЕ плодим.
- **Производные (C: солод/мука/настойка/экстракт)** → препарат-из-источника:
  голый «солод» = родовой по злакам либо NULL; «ржаной солод» → рожь через
  уточнение. Смежно с `_PART_WORDS`/обработкой препаратов. Отдельная меньшая
  фаза, позже.

## 6. MCP-контракт родового узла (решено: определить)

`get_plant` на родовой строке:
```
{ rank: "genus",
  name: "Вишня", name_latin: "Cerasus",
  members: [{id, name, name_latin, epithet}],          // виды-члены
  aggregated_uses:     [{use, species:[...], source}],  // union + атрибуция
  aggregated_compounds:[{compound, species:[...], source}],
  recipes: [...],                                        // родовые упоминания
  note: "род; рецепты с недоопределённым именем линкуются сюда" }
```
`search_plants` возвращает `rank`, чтобы агент мог drill-down. Резолв родового
ингредиента помечается «matched at genus level». Видовой `get_plant` получает
`parent: {id, name}` для подъёма к роду.

## 7. Связь с существующей машинерией

Ничего нового по сути — дособираем из готового:
- `_identity` (noun/adj) — детектор родовости и сборщик токенов.
- `merge_plants_by_latin_key` / `_latin_key` — латинский род для валидатора 4.2;
  родовые строки инертны к видовому dedup (`_latin_key` рода = 1 токен → None).
- денилист `_NON_PLANT_SUBSTANCES` — домен A, уже в проде-матчере.
- `compounds.parent_id` — готовая иерархия для домена веществ.
- `identity_conflict` (toxic+edible) — доп.сигнал импостера D (физалис-паслён
  токсичен, вишни нет).

## 8. Эффекты вниз по стеку

- Чистые видовые монографы (родовые рецепты больше не липнут к войлочной вишне).
- Родовая страница/монограф «вишни вообще» с drill-down.
- Родовой контракт MCP — агент видит категорию и выбирает.
- Квесты: тема «прогулка за вишнями».

## 9. План постройки (correctness-first, не срочный патч)

1. Схема: `rank` + `parent_id` на `plants` (миграция), индексы.
2. Сборка родов (durable Temporal workflow, commit-per-genus, resume): по корпусу
   собрать токены с ≥2 видами → классифицировать (a/b/c/d) → создать родовые
   строки (a), проставить `parent_id` членам, спорные/c/d → review-находки.
3. Матчер: голый родовой токен → родовая строка; специфичное → вид; (c)/(d) →
   NULL+флаг. Re-link корпуса (durable workflow, как нынешний relink).
4. View/монограф родового узла (агрегация с атрибуцией) + MCP-контракт (§6).
5. QA-чеки (в линтер качества): родовая строка без членов; вид без рода при
   наличии родового токена; импостер по латыни; токен (c) без флага.
6. Вещества (домен A) через `compounds.parent_id` — отдельно.
7. Производные (C) — отдельная поздняя фаза.

Юзеров нет → не боимся массового апдейта карточек; гоняем чеки до приемлемого.

## 10. Решения и открытые вопросы

Решено: (1) род = хаб без своих фактов, агрегирует с атрибуцией; (2) MCP-контракт
определить (§6); (3) порог родовости = ≥2 различных вида.

Вторичные открытые: каноникализация русского родового имени, когда у членов
разные головы (черешня/вишня); показывать ли (c) disambiguation-set или просто
NULL; нужен ли родам собственный qdrant-вектор (склоняюсь: нет, поиск через
членов).

## 11. Не-цели

Не строим внешнюю таксономию/ранги выше рода (семейство и т.д.) — только род↔вид
под текущую боль. Не трогаем специфичные ссылки, которые и так резолвятся верно.
Не изобретаем фактов на родовом узле.
