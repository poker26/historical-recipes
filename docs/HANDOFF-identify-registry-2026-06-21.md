# HANDOFF → мобильный агент: `registry` на кандидатах определения

**От:** backend-агент. **Дата:** 2026-06-21.

## Что нового
`POST /api/identify` (и MCP `identify_plant`) теперь, для кандидата, у которого **нет нашего монографа** (`plant: null`), но который ЕСТЬ в авторитетном реестре флоры (свод Черепанова 1995, ~24.7k принятых видов + синонимы), добавляет блок:

```jsonc
{
  "latin": "Acer rubrum", "score": 0.71, "plant": null,
  "name_ru": "…", "inat_taxon_id": 12345,        // как раньше (iNat)
  "registry": {                                   // ← НОВОЕ
    "status": "accepted",                         // "accepted" | "synonym"
    "accepted_latin": "Acer rubrum",              // принятое имя (у synonym может быть null, если связь в своде нечитаема)
    "family_latin": "ACERACEAE"
  }
}
```
В корне ответа — `registry_count` (сколько кандидатов опознано реестром).

## Зачем / как показывать
Это решение «реестр-как-полнота, без пустых карточек»: вместо тупика «нет в нашей базе» — честное **«известный вид флоры России (по Черепанову), монограф готовится»**. 
- `plant != null` → как сейчас (полная карточка-монограф).
- `plant == null && registry` → показать вид как **узнанный**: латынь + `family_latin` + (если есть) принятое имя; подпись типа «Есть в реестре флоры РФ, монографа пока нет». НЕ «не найдено».
- `plant == null && !registry` → как сейчас (вне реестра: iNat-имя/фото, либо честное «не определилось»).

Карточек-заглушек в браузинге/квестах НЕ появляется — реестр живёт только как слой узнавания; полноценную Plant-строку заведём, когда у вида появится контент (ленивый минт).

## Менять на клиенте
Опционально: рендерить `registry`-состояние на экране результата определения (третий вид карточки между «полный монограф» и «не найдено»). Контракт `identify` в остальном не изменился.
