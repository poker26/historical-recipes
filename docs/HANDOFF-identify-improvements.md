# HANDOFF — определение: матч-по-вероятности, пагинация «Рядом», грибы

Дата: 2026-06-19. От мобильного → backend-агенту. Три улучшения, все требуют серверной части
(клиент подключу следом, как делали с cold-start nearby). Источник правды по каждому — сервер.

---

## Q1. Матч по вероятности: near-tie + род, не только top-1

**Сейчас.** И клиент, и зачёт значка берут СТРОГО top-1 и требуют точного совпадения вида:
- клиент: `candidates.firstOrNull()` → `latinNorm(top.latin) == latinNorm(target)` (`Quest.kt:296`);
- сервер (зачёт): `badge_progress` берёт `identifications.top_latin` и проверяет `_latin_key(top_latin) ∈ species_set` (`services/quests.py:331-339`).

**Проблема.** Движок (Pl@ntNet) для родственных видов (Achillea millefolium ↔ nobilis) почти случайно
ранжирует сиблингов; разница 45% vs 44% = шум. Юзер с верным видом получает «не тот» И **не получает
зачёт значка** (т.к. `top_latin` = сосед).

**Изменить (сервер = источник правды).** Полный список кандидатов уже хранится в
`identifications.candidates` (JSONB) — использовать его, а не только `top_latin`:
- член набора `k` засчитывается, если СУЩЕСТВУЕТ кандидат `c`: `_latin_key(c.latin)==k` И (`c` — ранг-1
  ИЛИ `c.score >= top_score*0.85`) — т.е. цель в топе или near-tie (зазор ~15%, настраиваемо).
- **родовой «почти»** (рекомендую, по решению юзера — великодушно): если род топ-кандидата совпал с
  родом члена набора, но вид иной → засчитывать как мягкое попадание (цель игры — «встретил
  тысячелистник в этом месте», а не экзамен по виду).
- `badge_progress` сейчас SQL-агрегирует `top_latin` — проще переписать на чтение `candidates` (Python-
  фильтр по JSONB) ИЛИ при архивации писать доп. поле `matched_set_keys` (предрасчёт на стороне записи).
- чтобы клиентское ✓/✗ совпадало с зачётом: вернуть в ответе identify (или отдельным полем) тот же
  вердикт, ИЛИ просто задокументировать правило — клиент применит идентичную margin-логику к
  `candidates` сам (у меня они есть).

**Клиент (после).** `shootFor` → near-tie/род = «✓ засчитано» / «похоже, засчитано»; иначе честный
«не похоже». Сообщение строго совпадает с серверным зачётом.

## Q2. «Рядом»: глубже пул + пагинация (сейчас тупик)

**Сейчас.** `nearby()` (`services/quests.py:174`) ранжирует большой iNat-пул по тирам (биотоп+корпус →
корпус → iNat), но **обрывает на `target=5`** (`if len(items) >= target: break`), остальных
выбрасывает. Эндпоинт `/quests/nearby` отдаёт 5. Если этих 5 рядом не растёт — рефреша нет, юзер уходит.
(В квестах не тупик: страница места отдаёт ВЕСЬ `species_set`.)

**Изменить (сервер).** Отдавать глубже — пул уже посчитан:
- добавить `limit` (default ~15) ИЛИ `offset` к `/quests/nearby`; не обрывать на 5, вернуть до ~15
  ранжированных (тир-порядок сохранить). Payload 15 с фото — ок.
- рекомендую `limit=15` одним ответом (минимум вызовов iNat) + клиент листает по 5 локально.
- опционально вернуть `has_more`/общий размер пула, чтобы клиент знал, показывать ли «ещё».

**Клиент (после).** «Рядом» показывает 5 + кнопка «Показать другие 🔄» (следующая пятёрка из
загруженного), в конце — «Это всё, что растёт рядом сейчас» + «Обновить» (перезапрос, шире радиус).

## Грибы: второй движок (Pl@ntNet их не видит)

**Проверено.** Бридж kingdom-корректен: латынь гриба резолвится в наш гриб-монограф, `kingdom`
переносится (`routers/identify.py:_bridge`). НО движок = **Pl@ntNet, только растения** (`services/
plant_id.py`, любой project = флора). Фото гриба → 404 «no species matched» или мусорные растения →
до (корректного) гриб-бриджа не доходит. Грибы в корпусе есть, но по камере недостижимы.

**Изменить (сервер).** Движок явно one-file-swappable (контракт `identify()` → `{candidates:[{latin,
score,...}]}`). Добавить грибной движок за тем же контрактом:
- **РЕШЕНО: Kindwise Mushroom.id.** Ключ получен и проверен 2026-06-19 (usage_info → 200, `active:true`,
  50 кредитов, 1 кредит = 1 определение). **Ключ НЕ в репозитории** — лежит в чате/vault `vds/kindwise`
  (подставить в backend env `KINDWISE_API_KEY`; юзеру перевыпустить — светился в чате).
- **API:** base `https://mushroom.kindwise.com/api/v1`, auth заголовок `Api-Key: <key>`. Определение —
  `POST /api/v1/identification` (body: `images` base64 + опц. `similar_images`, `details`), возвращает
  `result.classification.suggestions[].{name (латынь), probability}` → маппить в наш контракт
  `{latin, score}` и дальше в существующий `_bridge` (kingdom разрулит). Баланс — `GET /api/v1/usage_info`
  (бесплатно). Готовый Python SDK: `flowerchecker/kindwise-api-client` (`pip install kindwise-api-client`).
- ⚠️ прод-egress к внешним API заблокирован — Pl@ntNet ходит через trusttunnel-прокси; Kindwise пустить
  через тот же прокси (как `plantnet_proxy`). С локалки/Windows egress к kindwise РАБОТАЕТ (проверено).
- роутинг v1: явный тумблер «это гриб» на экране съёмки → вызвать грибной движок (дёшево и понятно;
  без угадывания). Бридж не трогать (kingdom разрулит).
- **SAFETY-ГЕЙТ (критично).** Определение грибов по фото = смертельные двойники (бледная поганка ↔
  шампиньон). НЕ выкатывать грибной режим без safety-блока, заполненного для грибов (L0-L4 +
  «опасный двойник» + жёсткий дисклеймер «не употреблять по фото»). Тот самый safety-блок, что мы
  вывели первым на карточке — он обязателен здесь.

**Клиент (после).** Тумблер «это гриб» → грибной движок; результат ведёт в гриб-монограф; громкий
safety-дисклеймер.

**План Б по движку (если Kindwise по объёму выйдет дорогим).** Движок one-file-swappable (`identify()`),
vendor-lock минимальный. По убыванию приоритета:
- **Self-hosted FungiCLEF-модель** — открытые модели/код соревнования FungiCLEF 2022–24 (упор на ЯДОВИТЫЕ
  виды; HuggingFace/Kaggle/GitHub, напр. DS@GT). Ноль стоимости за вызов, крутится на ML-боксе server 2
  (там уже BGE-M3). Апфронт: деплой + ОБЯЗАТЕЛЬНАЯ валидация точности. Лучший вариант при росте объёма.
- **MyShroom API** (github MyShroom/myshroom-api) — сторонний грибной движок; проверить цену/качество.
- **Custom-классификатор** (Roboflow / Nyckel / Vertex AutoML) на датасете FungiCLEF — pay-per-call или self-host.
- ❌ iNat CV — полная модель закрыта (IP + ARR-фото), публично ~500 таксонов, коммерческого API нет.
- ❌ Generic cloud-vision (Google/Azure/AWS) — нет видового определения грибов из коробки.
- 💡 У Kindwise попросить скидку за меньшее число классов (`support@kindwise.com`) — нам нужны
  съедобные/ядовитые/лекарственные, не все 3100 видов.
- ⚠️ ЛЮБОЙ движок — только с safety-гейтом; более дешёвый/свой — только после валидации точности
  (ошибка по грибу может убить).

## Решения — ЗАКРЫТЫ (можно стартовать)
1. ✅ **Грибной движок:** Kindwise Mushroom.id, ключ получен+проверен (см. выше; в vault `vds/kindwise`).
2. ✅ **Великодушность Q1 подтверждена (2026-06-19):** near-tie в топ-3 (зазор ~15%) + родовой матч =
   ЗАЧЁТ значка. Лучше не отшивать верные находки (игра-открывалка, не экзамен).
3. **Порядок:** Q1 → Q2 (быстрые) → грибы (больше работы + safety-гейт + ключ).

## Деление работ
Backend-агент: серверные части всех трёх (зачёт по candidates+margin+род; deeper-nearby с limit;
грибной движок за `identify()` + safety-гейт). Мобильный агент: клиентскую обвязку подключит ПОСЛЕ
появления контрактов (сообщение матча в `shootFor`, пагинация «Рядом» + «Показать другие», тумблер
«это гриб» + дисклеймер) — как с cold-start nearby.
