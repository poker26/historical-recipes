## Часть 1 — ЗАПРОС К БЭКЕНДУ (actionable): пагинация прогулки «Ещё растения рядом»

**Зачем.** Прогулка отдаёт топ-5 видов и детерминирована → когда юзер «закрыл» все 5,
продолжить нельзя (а вне зоны бейджей это вообще единственный контент). Клиент при 5/5
показывает финал-плашку и хочет кнопку **«Ещё растения рядом»**.

**Что нужно.** В `GET /api/quests/walk` добавить пагинацию по тому же ранжированию:
- параметр `count` (сколько вернуть, дефолт 5) и/или `offset` (сколько пропустить),
  **или** `exclude=latin_key,latin_key,…` (виды, что клиент уже показал) — что проще на
  iNat `species_counts` (там есть `page`/`per_page`).
- Семантика: следующая пачка по убыванию частоты, тот же адаптивный радиус/узнаваемость/
  theme-safety. Конец списка → пустой `items` (клиент покажет «рядом больше нет»).
- Бэкенд-код: `build_walk(..., target, offset?)` уже почти готов (target есть; добавить
  пропуск/страницу в `_species_counts`).

Не блокер для остального; чисто расширение существующего эндпоинта.

## Часть 2 — ПЛАН: баллы за бейджи + leaderboard (дизайн, решения нужны)

### Принципы (из проекта — не нарушать)
- **Идентичность silent UUID, без аккаунтов/PII/логина.** Leaderboard анонимный/
  псевдонимный. Ник — авто-генерируемый, опционально меняется в настройках (PATCH
  `/devices/{key}/nickname` уже есть). Никакого обязательного ввода.
- **Награда = редкость/статус, инфо не гейтится.** Баллы — это сопоставимый «счёт»
  поверх бейджей, а не плата за контент.
- **Античит бесплатно:** баллы считает СЕРВЕР из уже верифицированных бейджей
  (`quest_issued_badges`) / гео-определений. Клиент НИКОГДА не присылает свой счёт.
  Фарм требует реально ходить и фотографировать в окне — ограничено самой реальностью.

### Что даёт баллы (предложение)
Баллы должны отражать **редкость**, а не объём (иначе побеждает спамер фоток). Основа —
**бейджи**, взвешенные по дефициту:
- **База за бейдж** (напр. 100).
- **Бонус за раннесть** по `ordinal` (он уже есть и фиксирован): #1 — самый ценный.
  Напр. `+max(0, 60 − ordinal)` или тиры (#1 +100, top-10 +50, top-50 +20).
- (опц.) **Бонус за полный набор** (matched = set_size, а не только target).
- Баллы бейджа **фиксируются в момент claim** (ordinal известен) → счёт не «протухает».
- (опц., для casual) маленькие баллы за ПЕРВОЕ определение нового вида — чтобы и без
  бейджей был прогресс; но мало, чтобы не перебивало редкость.

### Leaderboard — срезы (предложение)
- **Per-place** («топ-исследователи Битцевского парка») — самый вовлекающий.
- **Global all-time** — общий зал славы.
- **Seasonal** (текущий месяц/год, сбрасывается) — даёт новичкам шанс, держит свежесть.
- Показываем: ник + счёт + число бейджей + «ты #N из M». Никаких гео-следов/PII.

### Открытые вопросы (РЕШИТЬ до стройки)
1. **Источник баллов:** только бейджи (редкость), или + лёгкие действия (прогулка
   пройдена / первый вид)? (Рек.: бейджи основа, чуть-чуть за первый вид.)
2. **Модель редкости:** раннесть (`ordinal`) vs дефицит (мало владельцев) vs фикс за
   бейдж. (Рек.: раннесть, зафиксировать при claim.)
3. **Срезы leaderboard:** per-place + global + seasonal — все три или начать с одного?
4. **Ник:** авто («Зелёный Бегемот #4271») + опц. смена в настройках — ок?
5. **Сезонный сброс:** счёт обнуляется по сезонам или копится вечно (+ отдельный
   сезонный)?

### Поверхность (когда решим — что строить)
**Бэкенд:** функция `badge→points` + агрегат на устройство; `GET /api/quests/leaderboard
?scope=global|place|season&place_id=&period=` → `{me:{rank,score,badges}, top:[{nick,
score,badges}]}`; авто-ник + дефолт. Всё серверно.
**Клиент:** экран leaderboard (вход из «Прогулок»); показ баллов при выдаче бейджа
(«+120, ты #3 в Битце») и на полке; опц. смена ника в настройках.

**Статус:** план. Реализацию НЕ начинаем — ждём решений по 5 вопросам выше.
